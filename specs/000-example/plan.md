## Summary

This plan covers the implementation of a complete user authentication system for a Node.js/TypeScript REST API. The approach uses industry-standard JWT tokens (short-lived access tokens + long-lived refresh tokens), bcrypt for password hashing, and SQLite for persistence in development. The architecture is kept intentionally flat — no microservices, no event systems — to satisfy the Simplicity Gate.

## Implementation Phases

### Phase 0: Research

> Output: `specs/000-example/research.md`

- [x] Evaluate JWT libraries: `jsonwebtoken` vs `jose` vs `@auth/core`
- [x] Evaluate password hashing: `bcrypt` vs `argon2` vs `scrypt`
- [x] Evaluate SQLite drivers: `better-sqlite3` vs `@libsql/client`
- [x] Evaluate request validation: `zod` vs `joi` vs manual
- [x] Document decisions in `research.md`

**Key decisions made**:
- `jsonwebtoken` — most widely used, well-audited, simpler API than `jose` for this use case
- `bcrypt` (via `bcryptjs`) — battle-tested, widely understood, sufficient for this scale
- `better-sqlite3` — synchronous API fits Node.js single-thread model well; avoids async complexity
- `zod` — TypeScript-first validation with excellent type inference

---

### Phase 1: Design

> Output: `data-model.md`, `contracts/api.md`, this `plan.md` (updated)

#### 1.1 Data Model
- [x] Define `users` table (id, email, password_hash, verified, locked_until, failed_attempts, created_at)
- [x] Define `sessions` table (id, user_id, refresh_token_hash, expires_at, revoked, created_at)
- [x] Define `password_reset_tokens` table (id, user_id, token_hash, expires_at, used, created_at)
- [x] PII identified: `users.email` — stored as lowercase, never logged
- [x] Documented in `data-model.md`

#### 1.2 API Contracts
- [x] `POST /auth/register` — create account
- [x] `POST /auth/verify-email` — verify email with token
- [x] `POST /auth/login` — authenticate, return tokens
- [x] `POST /auth/logout` — revoke refresh token
- [x] `POST /auth/refresh` — issue new access token
- [x] `POST /auth/forgot-password` — send reset email
- [x] `POST /auth/reset-password` — apply new password
- [x] Documented in `contracts/api.md`

#### 1.3 Architecture Decisions
- [x] **Token storage**: Refresh tokens stored as bcrypt hashes in DB (not plaintext). Access tokens are stateless JWTs — not stored.
- [x] **Account lockout**: Implemented as `failed_attempts` counter + `locked_until` timestamp on the `users` row. No Redis required.
- [x] **Email verification**: Token is a random UUID stored in a `verification_tokens` column on `users`. Expires in 24 hours.
